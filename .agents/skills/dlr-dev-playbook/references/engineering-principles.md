# 工程原则：想清楚再做

行为准则，用于降低 LLM 编码的常见错误模式。**取舍：偏向谨慎而非速度**；trivial 任务按判断从简。

## 1. 编码前先想：不假设、不藏困惑、外显权衡

动手前：

- 显式陈述假设；不确定就问。
- 存在多种解读时把它们都摆出来，不要默默挑一个。
- 存在更简单方案时说出来；该顶回去就顶回去。
- 有不清楚的地方就停下，指名道姓说出「哪里不清楚」，再问。

### 1b. 存疑消解顺序（停下来问之前，先按序本地消化）

大多数「不清楚」都能在本地解决。**按顺序消费以下来源，再决定是否停下来问**：

1. 项目指令文件（`AGENTS.md` / `CLAUDE.md` / `CODEBUDDY.md`）——尤其是「已知坑 / 防回归」章节。
2. 项目架构文档（`CODE_WIKI.md`、`docs/agent-reference/*.md`）。
3. 该模块自身的头部注释**和它的测试**——测试编码了预期行为与回归锁。
4. 触碰同一文件的近期提交。

**只有**满足下列任一条件才停下来问：

- 决策不可逆或外部可见（删文件、force-push、改公开接口、向他人/外部系统发送内容）。
- 需要只有用户才知道的信息（凭据、目标平台/房间/账号、预期的产品语义）。
- 仓库内两个权威来源互相矛盾。

其他情况：选证据最充分的那个方案实现它，并**在最终回复里写明假设与回滚方式**。
沉默猜测仍然禁止；变的是默认值——从「研究 → 停下」改成「研究 → 决策 → 披露」。

## 2. 极简优先：解决问题的最小代码，不写 speculative 的东西

- 不超出被要求的范围加功能。
- 不为只用过一次的代码做抽象。
- 不加没被要求的「灵活性 / 可配置性」。
- 不为不可能发生的场景写错误处理。
- 写了 200 行而它本可以 50 行 → 重写。

自问：「资深工程师会说这个过度设计吗？」会 → 简化。

## 3. 外科手术式改动：只碰必须碰的，只清理自己的烂摊子

编辑既有代码时：

- 不「顺手改进」相邻的代码、注释、格式。
- 不重构没坏的东西。
- 匹配既有风格，哪怕你自己会写成另一种样子。
- 发现无关的死代码 → 提出来，不要删。

自己的改动制造出孤儿时：

- 移除**你的改动**导致不再被使用的 import / 变量 / 函数。
- 既有死代码未经要求不动。

检验标准：**每一行改动都要能直接追溯到用户的请求**。

## 4. 目标驱动执行：先定义成功标准，再循环到验证

把任务翻译成可验证的目标：

- 「加校验」→「先为非法输入写测试，再让测试通过」
- 「修这个 bug」→「先写一个能复现它的测试，再让测试通过」
- 「重构 X」→「重构前后测试都要通过」

多步任务先给出简短计划：

```text
1. [步骤] → 验证：[检查点]
2. [步骤] → 验证：[检查点]
3. [步骤] → 验证：[检查点]
```

成功标准足够强，才能独立循环；标准弱（「让它能跑」）就会不断需要澄清。

## 与本项目其他配方的衔接

- 修日志缺陷时，「只修缺陷、不优化正常回退路径」是本节第 3 条的具体化 → `log-fault-triage.md`。
- 写测试时，「禁止在测试里自我实现被测逻辑」是本节第 3 条的反面约束 → `testing-conventions.md`。
- 动手前判断该不该做设计评审 → `design-brainstorming.md`。

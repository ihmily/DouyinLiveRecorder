# 排查、修复与验收

## 1. 建立运行时清单

按用户范围列出服务、环境、部署单元、运行时来源、版本证据及负责人。检查 `.nvmrc` / `.node-version`、`package.json` 的 `engines`、Dockerfile 各阶段、CI 工作流和部署配置。声明版本是意图，镜像摘要与运行中进程才是部署证据。

对现有业务进程，优先用已有诊断信息、启动日志或运维平台读取 `process.version`、`process.versions`、`process.execPath` 和构建标识，不为检查临时开放公网诊断接口。检查 PM2、systemd、容器、Serverless 与每个 worker 的实际二进制来源。`docker exec ... node --version` 仍然只代表新启动的 CLI，需要结合旧 worker 替换证据。

只运行用户信任的程序。避免导入项目入口、执行安装钩子或用 `npx` 下载“扫描器”。对仅能读取的仓库，明确“部署运行时未确认”。

## 2. 追踪 Brotli 与其他 CVE

可在授权仓库内先查线索：

```bash
rg -n --glob '!node_modules/**' --glob '!vendor/**' --glob '!dist/**' \
  'brotliDecompress|createBrotliDecompress|node:zlib|body-parser|inflate|Content-Encoding|fetch\(|undici' .
```

命中只是起点；继续确认实际依赖版本、默认行为、请求/响应路径和信任边界。没有命中仍可能由依赖内部解码。区分：

| 数据入口 | 要回答的问题 |
| --- | --- |
| 入站请求 | 是否有中间件自动解 `br`；代理是否解码或转发；绕过代理的路径是否存在 |
| 出站请求 | Fetch/Undici 或第三方客户端是否解码来自不可信站点/上游的响应 |
| 文件、队列、定时任务 | 攻击者是否能控制压缩输入；由哪个进程解码 |
| 嵌入式 Node | Electron、SEA 或其他产品是否绑定旧运行时；谁提供修复包 |

同时检查 DNS / TLS 校验使用位置、keep-alive 客户端、使用随机值的 startup snapshot / SEA、Node 26 ZIP API、Permission Model。基于项目事实排序，不把 Brotli 临时缓解视为修复所有 10 个 CVE。

## 3. 形成最小变更

以下内容先作为方案提交，默认不直接操作生产。开发者确认前，只能准备报告和独立补丁文件供审阅，不能将变更应用到项目或运行环境。方案须列出目标环境、具体 diff/包/镜像、命令、影响、验证和回滚方法；明确确认后再执行。笼统的修复请求和访问权限不能替代方案确认。本地/测试确认不包含生产，生产发布/重启须明确目标与操作；相同已确认方案不重复询问，超出范围则补充确认。临时缓解和回滚也遵循此规则。

- 上游 Node：更新实际运行时及固定版本配置至官方当前支持、包含本次修复的版本；减少不必要的大版本跨越。EOL 项目选择支持分支并验证兼容性。
- 容器：更新最终运行阶段的基础镜像或包，重新构建并确认摘要；只更新 builder 不覆盖运行镜像。发布后核对全部副本与 worker。
- 系统发行版：查供应商安全公告、完整包版本与变更日志。动态链接 Brotli 时核对实际库包和进程加载版本；不要仅以 `node --version` 下结论。
- Serverless / 托管环境：确认平台修复状态、用户可选运行时与重新部署要求；提交平台不支持的精确 patch 版本可能无效。
- Electron / SEA：由对应产品升级或重建，重新生成受影响的快照/打包产物，不能用系统 Node 升级替代。

给出修改前后版本、受影响文件、兼容性检查、发布目标和可用的安全回滚方案。不要把旧的易受影响版本作为已解决安全问题的回滚状态。

无法立即升级时，针对已证明的路径阻断不可信解码。例如在实际解码前拒绝压缩请求，或对某条 body-parser 路径设置 `inflate: false`；它会拒绝压缩请求并可能破坏客户端兼容性，应做定向回归。这仍未覆盖出站响应、其他解码路径和其他 CVE。不要仅删除 `Content-Encoding` 头，压缩内容会被误解释。`Accept-Encoding: identity` 是协商意图，不能保证服务器不返回 `br`。停用响应压缩编码器也不等于关闭解码器。


### 镜像升级影响评估（提交方案前必填）

升级镜像可能同时改变运行时和底层环境。即使只改一个 patch tag，也不能直接判断为低风险。先对比当前与候选镜像的 tag、digest、来源和架构，再按实际差异说明影响；优先保持当前受支持分支、SAPI/运行模式和发行变体。不顺带切换 Alpine/Debian、glibc/musl 或运行时大版本。

使用已有构建声明、镜像元数据、包清单/SBOM、供应商发布说明等只读证据。缺少资料时写“未核验”及补证方法，不能编造变化或写“无影响”。拉取、构建、启动测试容器以及执行项目构建/安装钩子应纳入待确认的操作计划，不以检查名义提前执行。

| 评估项 | 必须说明的影响与验证 |
| --- | --- |
| 基础环境 | OS 发行版、架构、glibc/musl、OpenSSL、CA 证书、时区和系统库是否变化；可能影响二进制加载、TLS 连接、时间处理和外部命令 |
| 运行时与依赖 | Node 分支、原生 addon 的 ABI/预编译包、动态 Brotli、npm/pnpm 等构建工具版本是否变化；评估是否需重编译依赖，验证 DNS/TLS、请求解码及项目关键路径 |
| 启动与配置 | ENTRYPOINT/CMD、默认用户及 UID/GID、工作目录、配置路径、环境变量默认值、文件权限和卷挂载是否变化；验证启动、读写权限与健康检查，不输出凭证 |
| 构建与使用范围 | 同一基础镜像涉及的 Web、队列、定时任务等目标服务及副本；检查多阶段构建产物是否适配最终镜像，明确重建/发布范围，不自动扩展授权 |
| 可用性与容量 | 容器重建/替换对长连接、会话、在途请求、队列任务的影响；启动耗时、内存/CPU、探针、滚动策略与额外容量是否满足现有服务目标；中断时间无测量则标待测 |
| 数据与回滚 | 启动脚本是否执行迁移或改写持久卷、缓存/会话格式是否兼容旧实例；记录备份、迁移可逆性和回退条件，不能假设换回镜像就能恢复数据 |

在方案中用下表逐项列出实际变化，明确受影响资产与未核验项。没有相关变更的项目可写“不适用”并给出依据；不要求为本次修补进行无关的全系统升级。

| 当前 → 目标变化 | 受影响服务/组件 | 可能影响 | 证据或未核验项 | 测试与成功标准 | 发布/回滚安排 |
| --- | --- | --- | --- | --- | --- |

根据差异安排测试环境验证、灰度/滚动发布、观察窗口和停止条件。开发者确认应覆盖这些影响与验证安排；测试后若发现新的影响范围，先更新方案并补充确认再继续。回滚到含漏洞的旧镜像会恢复暴露；优先准备已修复的可用构建，确需回退时说明隔离措施和时限。数据迁移不可逆时不能宣称镜像可直接回滚。

## 4. 验收证据

1. 用正常业务数据完成目标路径回归，不使用漏洞触发数据。既检查成功请求，也检查临时拒绝策略下的预期错误与兼容性。
2. 记录修复后的镜像/包/产品构建和供应商补丁证据。重复离线版本检查仅验证版本层面。
3. 验证全部目标服务实例和 worker 已替换，运行进程版本及必要的库映射符合修复要求；快照/SEA 重新构建并实际部署。
4. 记录流量恢复、错误率、回归结果和剩余未知。未获授权发布、无法读取线上或只有本地 CLI 证据时，结论应停在相应阶段。

完成标准针对用户指定的目标范围，不扩大为“整个组织安全”。检查器不检测入侵；发现异常时保留证据并按用户事件响应流程处理。

# Code Review Remediation

## Overview

把一份审查报告变成经过验证的最小改动集合。报告是**过去某一时刻的快照**，不是待执行指令：每一条都要先对当前工作区重新取证，再决定改不改。

## 何时使用

- 用户给出报告文件（`CODE_REVIEW_*.md` / `DIAGNOSIS_*.md` / 审查 issue），要求「逐条整改」「收口」「按报告修复」。
- 用户给出一份审查摘要并要求「把这些问题修掉」。
- 整改过程中发现报告本身有过期项、判错项，需要如实区分「已修 / 已存在 / 未修」。

不适用：只做审查、还没有报告；单条已知位置的小修；用户明确要求的是重构或升级。

## 第一原则

每条发现都是**待验证假设**，只有三种可能结论：

1. **仍存在** —— 复现判据命中，才可进入修复。
2. **已修复** —— 工作区已满足判据（可能是并行会话或前序批次修掉的），记录即可，不动代码。
3. **报告不成立** —— 用干净基线自证报告所描述的「缺陷前状态」并不存在，或它描述的是设计如此。记录为「报告不成立」，**不得为了对齐报告而改代码**。

先复核再动手不是保守，是因为报告的 `file:line`、符号名、结论都会随并发编辑漂移。

## 工作流

### P0 冻结现场

先取一次工作区与历史状态，作为后续所有判断的基线：

```bash
git status --short
git log -1 --oneline
git diff --stat
```

- 记下报告绑定的基线 ref（报告头部通常写明审查时的 HEAD）。
- 若报告说明「审查期间仓库仍在变动」，则复核是**强制**步骤，不是可选优化。
- 若 HEAD 与工作区不一致（典型：冲突解决结果是未提交改动），在最终汇报里点明；不要代为提交。

### P1 分类与去重

- 原样保留报告编号、标题、严重级别；按严重度从高到低排序，同级保持报告出现顺序。
- 同族条目合并（同一根因、同一判据面），并注明合并来源编号。
- 分「必须修复」与「可选建议」；可选建议默认**不改**，除非用户明确要求。

### P2 逐条复核

- 为每条选一个**能区分三态**的命令，按发现类型查 `references/verification-recipes.md`。
- 「报告不成立」必须用基线自证，例如 `git show <ref>:<path>`、`git diff <ref> -- <path>`，不能只凭当前文件「看起来没问题」下结论。
- 无法唯一确定位置（缺文件、缺符号、描述含糊）→ 移入「待人工确认」，写明**缺哪一项具体信息**，严禁猜位置、猜修法。
- 复核结果先落表，再批量进入修复；不要把复核和修复混在同一轮里。

### P3 用锚点定位

- 锚点写成「路径 + 符号」（函数 / 类 / 常量 / 用例名）。行号只作提示：写前重新 grep 一次，因为同文件增删会让行号漂移。
- 修复后汇报里的定位，用实测得到的最新行号；不要回抄报告里的旧行号。

### P4 按严重度修复，每项最小 diff

- 一次只处理一个条目，只改与该条目直接相关的行；不顺手优化、不重排格式、不重构。
- **如果条目是「缺失的回归锁」：先恢复用例并立刻运行。**
  - 用例绿 → 生产侧本来就没坏，条目只是测试丢失。
  - 用例红 → 说明生产侧也一起回归了；按失败断言指出的缺口修生产代码，再重跑。
  - 不要因为「新加的用例失败」就去改用例让它变绿。
- 不得削弱或删除既有测试。确需改动既有用例时，在汇报里单列原因。
- 机械式批量改写（改名、替换锚点）只允许作用于 `git ls-files` 列出的跟踪文件，并且**先 dry-run 打印命中清单**。禁止遍历整棵树——gitignored 的工具状态目录（如 `.mimosa/`、`.qoder-credits/`、IDE 缓存）会被一起改写且难以精确还原。
- 不提交。冲突解决结果、索引变更（`git rm --cached` 之类）一律交回用户。

### P5 冻结代码，然后只跑一次门禁

- 所有编辑结束后再跑门禁；中间跑绿不算证据。
- 用项目唯一的门禁入口（例如 DouyinLiveRecorder 为 `python scripts/run_gates.py`；其他项目用其自身的唯一入口），**不要**在汇报或 Skill 里复制命令清单，避免与事实源漂移。
- 判据按项目完成定义：pytest 0 警告、覆盖率门禁、类型检查、静态检查全绿。
- 门禁失败就回到编辑；每轮修改后重新全跑，不挑单条。

### P6 结构化汇报

按 `references/report-template.md` 输出。要点：

- 每条都有状态，不允许「看起来改完了」这种模糊表述。
- 区分「代码已修」与「已验证」：真机 / 端到端未执行时，明确写「未执行 + 原因 + 应由谁做什么」，并且**不得宣布完成**。
- 交回项单独成节：需要用户决策的（产品取舍、CI 触发策略）、需要用户执行的（提交、`git rm --cached`、重新安装依赖）、需要真机条件的。
- 汇报收尾核对 `git status --short`，列出本轮新增的未跟踪文件与本轮删除的临时脚本；残留要显式说明。

## 状态词表

| 状态 | 含义 | 代码是否改动 |
|---|---|---|
| 已修复 | 本轮复现 → 修复 → 复验通过 | 是 |
| 已在工作区修复 | 本轮复核时已满足判据（前序或并行会话所修） | 否 |
| 已存在（无需改） | 报告要求的用例 / 机制本来就在 | 否 |
| 报告不成立 | 基线自证报告描述不实，或属设计行为 | 否 |
| 部分修复 | 同族里安全的部分已改，其余需真机 / 决策 | 部分 |
| 未修复（交回排期） | 复现成立，但风险或体量超出本轮范围 | 否 |
| 待人工确认 | 缺文件 / 符号 / 上下文，或需产品决策 | 否 |
| 未处理（交回用户） | 需用户执行的仓库操作（提交、索引变更） | 否 |

## 红线

1. **不代用户提交**，尤其不提交冲突解决结果；不擅自 `git add` 全量。
2. **没有端到端验证就不宣布完成**；报告里必须写清未执行原因与下一步动作。
3. **机械改写只碰跟踪文件**；改写前 dry-run 并保存命中清单。
4. **收尾只删自己产生的临时文件**；运行期产物目录与正式脚本一律不动。
5. **不缩小报告范围**：报告里没修的条目照样逐条列出状态，不许静默丢弃。

## 常见翻车（均有实测来源）

- **改名脚本溢出**：一次「只改引用」的脚本扫了全树，改了 844 个文件，其中一大批落在 gitignored 的工具状态目录（`.mimosa/` hook 快照、`.qoder-credits/`），事后只能靠哈希比对逐项评估。改用 `git ls-files` 白名单 + dry-run。
- **用危险命令字面量测守卫**：想验证 Hook 正则，却在 shell 里直接写待测的删除命令，被守卫当场拦下。改用临时脚本或守卫自带的 self-test 语料。
- **一次扫描器传裸相对路径**：`Path("msg_push.py").relative_to(ROOT)` 直接抛 `ValueError`。仓内扫描器一律从仓库根构造绝对路径（`git rev-parse --show-toplevel` 或 `__file__` 上溯）。
- **门禁早跑**：改到一半跑绿就继续改，收尾又没重跑。门禁只认最后一次编辑之后的运行。
- **抄报告行号**：报告里的 `file:line` 在并发改动后已经指到别的行。定位以符号为准。
- **把「报告判错」当「自己漏修」**：基线里本就正确的代码被「修正」，制造了新的回归。凡与基线矛盾，先判定报告不成立。

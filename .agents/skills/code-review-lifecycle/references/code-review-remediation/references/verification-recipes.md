# 取证判据：按发现类型选命令

每条发现只回答一个问题：**当前工作区是否仍然存在该缺陷？** 下面按常见发现类型给出能区分「仍存在 / 已修复 / 报告不成立」的命令。命令中的 `<ref>` 指报告绑定的基线提交，`<path>` 指报告点名的文件。

通用要求：

- 优先用只读命令，禁止在取证阶段写入。
- 判据要能复跑，汇报里附命令与读数，不只写结论。
- 仓内一次性扫描器从仓库根构造绝对路径，不要传裸相对文件名（`Path("x.py").relative_to(ROOT)` 会抛 `ValueError`）。

## 1. 钉定哈希 / 字节失配

报告称「文件内容与钉定表不符」。

```bash
python - <<'PY'
import hashlib, pathlib
p = pathlib.Path("<path>")
print(len(p.read_bytes()), hashlib.sha256(p.read_bytes()).hexdigest())
PY
```

- 与钉定表逐项比对，全部相等 → **已修复**（记录 `match=True`，不要为「对齐」改文件）。
- 不等 → **仍存在**；改哪一侧取决于钉定表是不是事实源，先看表旁的注释与调用点。

## 2. 用例 / 符号「不存在」

报告称某个回归锁、函数或常量缺失。

```bash
git grep -n "<symbol>" -- <path-or-dir>
git ls-files <path>
git show <ref>:<path> | grep -n "<symbol>"
```

- 工作区有 → **已存在（无需改）**。
- 工作区无、基线有 → 用例被删掉了，**恢复后先运行**（见下）。
- 工作区与基线都无 → 报告可能记错了名字，按搜索同义名再判；仍无则 **报告不成立** 或需人工确认。

## 3. 恢复回归锁后先跑

「缺失的回归锁」不是普通条目：它是**生产侧回归的探针**。

```bash
python -m pytest <test-file>::<test-name> -q
```

- 绿 → 生产侧完好，条目仅缺测试。
- 红 → 断言的失败信息指向的就是生产侧缺口；修生产代码，不要改用例迁就。
- 红的原因若是**用例本身依赖的辅助函数**崩了（枚举到 0 处、路径解析失败），先区分「枚举面定义失效」与「生产侧真缺」，再决定改哪边。

## 4. 配置重复键 / 解析器崩溃

报告称配置读取会抛异常或出现重复键。

```bash
grep -n "<key>" <config-file>
python - <<'PY'
from <module> import <public_reader>
print(<public_reader>())
PY
```

- 只数文本出现次数不够：必须调用**生产入口**复现，才说明用户路径是否真的会崩。
- 修完再调一次，读数为成功且键只出现一次才算修复。

## 5. HTML / 文本结构损坏

报告称文件首尾有孤立标签、重复闭合。

```bash
python - <<'PY'
import pathlib
b = pathlib.Path("<path>").read_bytes()
print(b[:60])
print("</body>", b.count(b"</body>"), "</html>", b.count(b"</html>"))
PY
```

- 首字节应是文档声明而非闭合标签；闭合标签各出现 1 次。
- 结构类修复补一条结构断言用例，防再次被截断/拼接。

## 6. 悬空锚点 / 改名残留

报告称注释或文档引用了已改名的文件 / 用例。

```bash
git grep -n "<old-name>"
git ls-files | grep "<new-name>"
```

判定前先排除三类**不应改**的命中：

1. 变更日志 / 历史文档里对旧名的记录（历史事实）。
2. 文件头自述（不是跨文件引用）。
3. 报告本身明确排除的范围。

剩下的才是需要改的引用；改名类修复同样遵守「只碰跟踪文件 + dry-run」。

## 7. 文档与事实源矛盾

报告称文档写的值 / 行为与配置或 workflow 不符。

1. 先读**事实源**（`pyproject.toml`、workflow、检查脚本常量），再读文档。
2. 以事实源为准改文档；若「哪边才是对的」属于产品决策（如 CI 是否自动触发），不要自己选边 → **待人工确认**。

## 8. 门禁阈值 / 计数断言

报告称某个 `assert len(...) >= N` 与实际数量不符。

```bash
python - <<'PY'
import tomllib, pathlib
data = tomllib.loads(pathlib.Path("pyproject.toml").read_text(encoding="utf-8"))
print(len(data["project"]["dependencies"]))
PY
```

- 不要照抄报告里的数字；从事实源重新取数。
- 修复优先「按事实源动态取数」，而不是把常量改成当前读数——后者下次依赖变动又会漂移。

## 9. HEAD 含冲突块 / 解决结果未提交

```bash
git grep -c '^<<<<<<< ' HEAD
git grep -c '^<<<<<<< '
git status --short | head
```

- HEAD 有、工作区 0 → 缺陷已在工作区解决但**未提交**；状态记「未处理（交回用户）」，不代提交。
- 两者都有 → 仍存在，但同样属于用户的仓库操作，不要自行执行合并/提交。

## 10. 基线对比（判定「报告不成立」）

任何「这段代码本来应该长这样」的指控，都先用基线自证：

```bash
git show <ref>:<path> | head -40
git diff <ref> -- <path>
```

- 基线里就是报告所称的「异常形态」→ **报告不成立**（设计如此或报告误解），不改。
- 基线正常、工作区异常 → 确属回归，继续修。
- 基线也找不到该文件 → 报告与仓库版本错配，整条移入待人工确认。

## 三态判定速查

| 证据 | 结论 | 动作 |
|---|---|---|
| 判据在当前工作区命中 | 仍存在 | 进入修复 |
| 判据已满足，且与基线一致 | 已修复 / 已存在 | 记录，不改 |
| 基线与工作区都满足判据，报告称不满足 | 报告不成立 | 记录，不改，写明自证命令 |
| 无法唯一定位文件/符号 | 待人工确认 | 列出缺失信息 |
| 需用户执行的仓库操作 | 未处理（交回用户） | 给出一条可直接执行的命令 |

# 整改汇报模板

汇报面向「要拿它做决策的人」：每条发现都能回答三件事——**还在不在 / 改没改 / 谁还需要做什么**。

## 状态词表

逐条必填，不允许留空或写「已处理」。词表定义见 `SKILL.md`「状态词表」一节（唯一事实源，此处不复述）。

## 模板

```markdown
# <报告名> 整改汇报

> 报告条目：N 条（严重 a / 中等 b / 轻微 c）
> 基线：<报告绑定的 ref>；当前 HEAD：<sha> <subject>
> 工作区状态：<git status 摘要，例如 132 个已跟踪改动、2 个新增未跟踪文件>
> 说明：<如报告期内仓库有并发改动，在此声明复核为强制步骤>

## 一、分类与去重

- 必须修复：<编号列表>
- 可选建议：<编号列表，默认未改动>
- 合并的同族条目：<A ↔ B：合并理由>

## 二、逐项状态

| 编号 | 定位（路径 + 符号） | 证据（命令 / 读数） | 分类 | 状态 |
|---|---|---|---|---|
| S-01 | <path> :: <symbol> | `<command>` → <读数> | 必须修复 | 未处理（交回用户） |
| M-04 | <path> :: <symbol> | 恢复用例后 `2 failed` → 生产侧 23 处缺失 → 重跑通过 | 必须修复 | 已修复 |

定位用「路径 + 符号」；行号写成实测得到的当前值，不抄报告旧行号。

## 三、改动清单

| 文件 | 改了什么（一句话） | 对应条目 |
|---|---|---|
| <path> | <最小 diff 描述> | M-04 |

## 四、验证

| 项 | 命令 / 入口 | 读数 | 结论 |
|---|---|---|---|
| 门禁 | <项目唯一门禁入口> | <rc / 告警数> | 通过 |
| 单元测试 | `pytest` | <passed / skipped / warnings> | 通过 |
| 覆盖率 | <覆盖率门禁命令> | <总覆盖率 / 模块数> | 通过 |
| 类型检查 | <命令> | <error / warning> | 通过 |
| 端到端 / 真机 | <命令或场景> | 未执行 | 见交回项 |

门禁读数必须来自**最后一次编辑之后**的运行。只改了文档 / 注释时，注明按项目完成定义豁免了哪些步骤。

## 五、交回项

| 条目 | 需要谁做什么 | 具体动作 | 不做的后果 |
|---|---|---|---|
| S-01 | 用户 | `git commit` 提交已解决的冲突结果 | 仓库仍处于不可克隆状态 |
| S-06 | 用户 / 有真机条件者 | 用真实 URL 跑一次录制并确认退出时管道关闭 | 只证明了接线，未证明行为 |
| M-09 | 用户（产品决策） | 选择恢复 CI 自动触发，或改文档为「仅手动」 | 文档与 workflow 继续互相矛盾 |

## 六、未编号观察项

报告正文之外顺带看到、但不在条目的问题：单列，不擅自修。

## 七、收尾

- 本轮新增未跟踪文件：<列表>
- 本轮删除的临时脚本：<列表，或「未产生临时文件」>
- `git status --short` 核对结果：<无预期外残留 / 残留路径与原因>
```

## 证据书写规则

1. **写可复跑的命令和读数**，不写「已确认」「应该没问题」。
2. 读数要能区分三态：`match=True`、`0 命中`、`2 failed`、`rc=1`，而不是「正常」。
3. 报告判错的条目，附上基线与工作区的对比命令，让读者能自行复核。
4. 未验证的部分写成「未执行 + 原因 + 应采取的动作」，不要用「理论上可行」代替。

## 汇报口吻

- 先给结论表，再给细节；不要用叙述掩盖未修项。
- 不把「可选建议」算进完成率，也不把「已存在」算成本轮成果。
- 报告里未修的条目照样列出状态——静默丢弃等于伪造成果。

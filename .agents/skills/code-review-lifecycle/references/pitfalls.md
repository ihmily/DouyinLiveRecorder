# 本流程实测踩过的坑

分两层：**工具层**（命令本身会骗你）已有独立 Skill 详述，这里只给症状与指路；**流水线层**（派发、复核、成稿）是本文件主体。

## 工具层 → 见 `dlr-dev-playbook/references/windows-readonly-source-probing/SKILL.md`

| 症状 | 去哪一节 |
| --- | --- |
| 门禁全绿，实际刚跑红过 | 该 Skill §1「退出码：绝不用管道后的 `$?`」——本流程硬规则 2 就是它 |
| `syntax error` / `unexpected EOF while looking for matching` 且代码看上去没问题 | §2「含转义内容的探针」——引号、反斜杠、反引号会被工具层吃掉 |
| 脚本 rc=0 却没产出 | §3「路径归一」——bash 的 `/tmp` 不等于 Windows 解释器的 `/tmp` |
| `open()` 泄漏探针报出上百处假阳性 | §4「AST 判定：按节点身份」——`with open()` 与裸 `open()` 的 `ast.dump` 文本同形 |
| 定点 pytest 之后仓库多出 `.coverage` / `.pytest_cache` | §5「定点 pytest：不留覆盖率与缓存」 |

本流程里这些坑出现的位置很固定：阶段 1 取基线、阶段 2 跑范围脚本、阶段 5 复跑判据、阶段 7 收尾自证。踩到时不要现场发明修法，按那份 Skill 的配方走。

## 流水线层

### 1. 拿损坏的 HEAD 当基线 → 成批假「丢失」

**症状**：报告写「丢了 18 条用例 / 少了 4 个模块 / 注释整段被删」，复核后发现东西都在。

**错误做法**：`git show HEAD:file` 或 `git diff HEAD -- tests/` 直接做集合差。

**正确做法**：先验 HEAD 自身是否干净（`git grep -c '^<<<<<<< ' HEAD`）；不干净就取**已知无冲突标记的祖先提交**作参照，且优先比 **AST 符号集合 / 用例名集合**，不比文本行。结论要落到具体文件与具体用例名，不能停在总数。

**判据**：基线提交上的 `grep -c 'def test_'` 与工作区逐文件相等，才允许说「没丢」；不相等则必须指出差集在哪个文件。

### 2. 审查期内别人在改盘 → 结论与现场对不上

**症状**：报告说某处有问题，用户打开时已经被修好了；或者同一文件在报告里有两个不同行号。

**错误做法**：只在开头取一次基线，中途不复比；把「期内被修掉」的项和本轮发现混在一张表里。

**正确做法**：基线用 `scripts/review_scope.py` 生成，中途和收尾各 `--check` 一次；每条结论写实测时刻；期内被别的包修掉的项**单列**成节（报告 §7.3），附修复时刻与复跑判据。

**判据**：收尾 `--check` 报出的漂移文件，必须能对应到报告里已登记的「期内变化」；对不上的就是未披露的污染。

**排除误判**：基线按**原始字节**求哈希。仓库若启用 `core.autocrlf`，一次 `git checkout` 还原就会把 LF 改成 CRLF，字节确实变了、报漂移是对的；先用 `git diff --ignore-cr-at-eol` 确认是否只差行尾，再决定记成「行尾漂移」还是「内容变化」。

### 3. 主控不复跑 → 假断言写进报告

**症状**：报告里出现「丢了 N 条用例」「35 行注释被整段删除」这类结论，随后被推翻。

**错误做法**：把代理回传当结论，最多换个措辞。

**正确做法**：所有「严重 / 中等」断言由主控独立复跑；推翻的写进 §7.2 三列表（子代理断言 / 主控复核实测 / 处理），并写明采纳的替代结论落在哪个编号。

**判据**：§7.2 为空不是好事，通常说明没复核。每条「不采纳」都要能看到一条主控自己跑过的命令与读数。

### 4. 代理自造白名单 → 真缺陷被豁免

**症状**：某个明显问题被代理写成「按项目约定如此」，主控照抄。

**错误做法**：在白名单里写「本项目的宽 except 是设计」却指不出出处；或让每个代理自行判断「什么是刻意的」。

**正确做法**：白名单集中在一份简报里，**每条带仓内出处**（AGENTS.md 章节 / CODE_WIKI 条目 / 测试锚点）。代理只能引用，不能新增；主控要新增也得先找到出处。

**判据**：随机抽 3 条白名单，能在仓内文件里定位到原文。

### 5. 逐文件遍历 git 历史 → 超时、被转后台、结论断在半截

**症状**：统计冲突块数量时命令跑了几分钟被移到后台，或对每个提交 `git show` 循环时挂住。

**错误做法**：`for c in $(git log …); do git show $c:file | grep -c …; done`，或 `git ls-files | xargs grep`。

**正确做法**：用 git 自带的批量检索一次统计：

```bash
git grep -c '^<<<<<<< ' HEAD | awk -F: '{s+=$NF; n++} END{print "blocks="s+0, "files="n+0}'
git grep -c '^<<<<<<< '          | awk -F: '{s+=$NF} END{print "worktree blocks="s+0}'
```

需要逐提交定位时，先 `git log --format=%h -n 20` 缩小候选，再对少数提交单独查。

**判据**：单条命令应在秒级返回；超过 30 秒就换形态，不要等着它「可能就快好了」。

### 6. 读子代理的 transcript → 上下文直接爆掉

**症状**：派发后想「看看它进展」，去 tail `output_file`，下一轮上下文被占满。

**错误做法**：Read / tail / grep 代理的 JSONL 流水。

**正确做法**：只等完成通知与回传正文；需要进度就用任务列表看状态。代理的完整流水是给调试平台用的，不是给主控读的。

**判据**：主控上下文里不应出现任何以 `{"type":"assistant"` 开头的成片 JSON。

### 7. 报告只有结论、没有复跑判据 → 无法复核

**症状**：读者想问「这个 899 块现在还是吗」，报告里只有数字，没有命令。

**错误做法**：把「实测」写成形容词，把「未执行」写成「应当没问题」。

**正确做法**：§8.3 逐条给 `命令 + 期望值 + 当前实测值`；§9 单列「未执行项声明」（未跑全量测试、未做真机、未联网核对 CI），并说明它们是哪些整改的验收前置动作。附录 A 写清覆盖边界：哪些文件逐行读过，哪些只被扫描覆盖。

**判据**：抽 §8.3 的任意两条，复制粘贴能跑出与报告一致的结果。

### 8. 把「未发现」当成「覆盖过」

**症状**：某个区回传「未发现问题」，主控就认为该区干净。

**错误做法**：接受一句「无发现」作为结论。

**正确做法**：要求代理回传**覆盖确认**（读了哪些文件与行区间、哪些没读）和**卫生扫描结果**（判据 + 命中数，0 也写「实测 0 处」）。没有这两样的「无发现」按未覆盖处理，在附录 A 里如实登记。

**判据**：报告附录 A 的「逐行精读覆盖」总数应接近范围表的代码行数；差得多的部分必须解释为什么。

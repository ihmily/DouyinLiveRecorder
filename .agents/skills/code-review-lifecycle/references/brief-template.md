# 共享作业简报模板

每个分区代理的 prompt 第一步都是 Read 这份简报。它取代「在每个 prompt 里重复一遍规则」——重复会漂移，漂移会让同一个约定在 A 区算缺陷、B 区算合规。

落盘位置：`%TEMP%/review-brief-YYYY-MM-DD.md`（**不要**落在仓库里）。收尾删除。

---

## 模板（复制后逐节填写）

````markdown
# <仓库名> 全仓静态审查 · 代理作业简报（YYYY-MM-DD）

## 0. 任务性质（硬约束）

- **只读审查**。严禁编辑、创建、删除、格式化仓库内任何文件；严禁运行 `black`/`isort` 的写入形态、
  `pytest --cov`、`pip install`、任何 `git add/commit/checkout/reset/stash/clean`。
- 允许：Read/Grep/Glob、只读的 `git show/log/diff/grep`、以及「只打印不写盘」的解释器单行片段
  （用 <解释器路径与版本>）。
- 不要在仓库内落任何临时脚本。需要探针时优先内联；确需脚本就写到 `%TEMP%` 并在回传里说明路径。
- 门禁 rc 用 `命令 >"$LOG" 2>&1; echo rc=$?`，不要用管道后的 `$?`。

## 1. 仓库当前状态（已实证，勿重复报告为新发现）

1. <HEAD 完整性：是否含未解决冲突块，判据命令与命中数>
2. <工作区与 HEAD 的关系：未提交改动数、是否刚被别的包改过>
3. <本轮已知的、不属于缺陷的既有状态>
4. 因此重点找：<例如「冲突解决过程留下的真实缺陷」：悬空引用、语义改错、孤立残留标记、重复定义>

> 这一节必须写**实测数字 + 取数命令**。代理会把已知状态当新发现，是最常见的噪声来源。

## 2. 本项目「刻意设计」白名单（命中即不报，或最多作为「轻微·备案」）

规则：**每一条都要能指出仓内出处**（AGENTS.md 章节 / CODE_WIKI 条目 / 测试里的锚点注释 / 历史审查报告）。
找不到出处的不进白名单——那不是刻意设计，是按缺陷评。

- <风格约定：注释形态、行宽、异常写法…> —— 出处：<文件#章节>
- <被误报最多的「宽 except」/「静默跳过」/「死代码保留」…> —— 出处：<…>
- <排除在审查范围外的目录与生成物> —— 出处：<…>
- <测试侧既有约定：替身形态、双模脚本、`tmp_path`、fixture 冻结…> —— 出处：<…>

DLR 实测样例（供对照形状，不要照搬内容）：

- 注释一律 `#`、禁止 docstring；行宽 120；`except A, B:` 无括号（PEP 758）。
- 托盘回调、清理段、看门狗里的宽 `except Exception` 已论证，不强制收窄。
- `src/javascript/crypto-js.min.js` 是第三方压缩库，审查范围外；`src/proto/douyin_pb2.py` 是 protoc 生成物（只评与 `.pyi` 存根是否同步）。
- `config/config.ini` 是**已跟踪的脱敏基线模板**，不是硬编码凭据。
- live collector 双模脚本的 `if __name__ == "__main__"` 与 argv 两步守卫是设计，不是缺陷。

## 3. 审查维度

1. 代码质量：可读性、重复代码、命名与结构、异常处理质量。
2. 潜在缺陷：空值/边界、资源泄漏（句柄/线程/进程/连接/队列无界）、并发与时序错误、错误吞噬、缺超时、缺上限。
3. 安全：注入（SQL/命令/路径/模板）、未校验输入、硬编码凭据、敏感信息入日志、不安全反序列化、XSS/CSRF/路径穿越/SSRF 与内网绕过、TLS 校验降级、权限与鉴权缺口。
4. 逻辑错误与死代码：恒真/恒假分支、条件写反、早退吞功能、不可达代码、未使用符号/import/重复定义、契约不匹配。

## 4. 严重度定义

- **严重**：进程崩溃 / 数据损坏 / 凭据泄露 / 安全防线失效 / 功能完全不可用；或提交态产物不可用。
- **中等**：特定条件下行为错误、资源持续增长、防线可被绕过、维护上会误导后人（含悬空引用一类）。
- **轻微**：可读性、命名、日志噪声、备案性观察。

## 5. 输出格式（严格按此回传，不要写文件）

先一行「**覆盖确认**」：列出实际读过的文件/行区间 + 未覆盖部分。
然后每条发现按：

```
[编号] 文件相对路径:L起-L止 | 类别(质量/缺陷/安全/逻辑) | 严重度 | 标题
证据：<≤3 行代码片段或精确符号名，必须来自实读>
影响：<一句话>
建议：<一句话，含改动点>
状态：已实证 / 待确认（说明缺哪一步）
```

要求：

- **每条行号必须来自你实际 Read 到的内容**，禁止推测行号。
- 同类问题合并：给「计数 + 全部文件列表 + 3~5 个代表位置」，不要逐条罗列 20 条同族。
- 最多回传 20 条，按严重度降序；宁缺毋滥。没有发现就明说「未发现 + 覆盖了哪些维度 + 用什么判据扫的」。
- 本区之外的发现另起一行标 `[越界]`，不计入 20 条。
- 另外回传 1 段「**范围性卫生扫描结果**」：你用的 grep 判据 + 命中数，
  命中为 0 也要写「实测 0 处」。
````

## 分区代理 prompt 骨架

每个代理的 prompt 只写**该区特有**的东西，通用规则靠简报：

```text
你是 <仓库名>（仓库根 <绝对路径>，<技术栈一句话>）本轮全仓静态审查的一个分区审查代理。

**第一步**：Read 共享作业简报 `<%TEMP% 绝对路径>`（只读硬约束、刻意设计白名单、严重度、回传格式）。
简报「仓库当前状态」已说明 <已知状态一句话>，重点找 <本轮真正的风险面>。

**审查范围（完整通读，用 Read offset/limit 分段读满）**：
- `<文件或目录>`（<行数> 行）—— <该区职责、关键子系统>
- <若切分：本区为 L1–L11000，后半由另一代理负责；若在 L11000 附近被切断，请说明确切断点>

重点判据（结合简报白名单，勿误报）：
1. <该区专属判据 1>
2. <该区专属判据 2>
3. <悬空引用/契约匹配等该区易错点>

**行号纪律**：发现行号必须来自实读。严禁修改/创建/删除任何文件；只读探针用 <解释器> 内联。
按简报 §5 回传，最多 20 条，含「覆盖确认」与「范围性卫生扫描结果」。
```

切分经验：每区约 2k–11k 行；超长文件按函数/类边界切，并在 prompt 里写明切点。相邻区要写「勿越界报告」，否则同一处会被两区各报一次。
